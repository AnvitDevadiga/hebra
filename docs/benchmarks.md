# Benchmarks

Everything here is reproducible from files in `benchmarks/`. Summary numbers
are generated by `benchmarks/summarize.py` from raw per-task records; nothing
is entered by hand.

## What is measured, and what is not

The benchmark measures **localization**: given a natural-language task, does
the packed context contain the code that needed to change? It does **not**
measure whether a coding agent succeeds. No agent experiments have been run
(no model credentials or cost approval were available); see
[Agent benchmark](#agent-benchmark).

## Dataset: `hebra-localization-v1`

- Repositories, pinned: `pallets/click` at `2247b35e`, `psf/requests` at
  `3c7baaa0`, `python-attrs/attrs` at `c8bb9bfa` (`benchmarks/configs/v1.json`).
- Tasks: 120 fix commits (40 per repository), mined by
  `benchmarks/mine_tasks.py` with a fixed rule: first-parent, non-merge
  commits, newest first; a subject of at least four words not matching
  release/docs/chore patterns; 1 to 3 non-test source files changed; 1 to 3
  labels. Re-running the miner reproduces `benchmarks/tasks/v1.jsonl` byte for
  byte (sha256 `4a13c525...`).
- **Task text**: the commit subject only. The patch, the commit body, and the
  fixed code are never given to retrieval.
- **Labels**: functions, methods, or classes whose lines the fix modified,
  resolved at the parent commit (innermost definition containing each
  modified line). This is a proxy for "the code that needed to change", not a
  complete list of useful context.
- **No leakage of the fix**: each task is indexed at the parent of the fix
  commit; the runner verifies the index revision equals that commit and that
  every label is a symbol in the index.
- **Subject names the target**: 26 of 120 subjects name a label as a whole word
  (for example "Fix `prepare_body` stream detection"). Results are reported
  for all tasks and separately for the 94 (held-out: 68) that do not.
- **Split**: `dev` (30 tasks) if `sha256(task_id)` mod 10 < 3, else `heldout`
  (90 tasks). Parameters were chosen on dev only.

## Metrics

Per task, then averaged over tasks with equal weight:

| metric | definition |
|---|---|
| symbol recall | labels whose line span overlaps a packed fragment / labels |
| any hit | at least one label overlapped |
| token precision | tokens of fragments overlapping a label / fragment tokens |
| utilization | used tokens / budget |
| redundancy | fragments adding no query term beyond earlier fragments / (fragments - 1) |
| references correct | fragments whose text equals the file at the stated lines |
| recall@k, MRR | over the first 50 retrieved chunks, chunk relevant if it overlaps a label |

Overlap means partial inclusion counts: a truncated function whose first lines
are present is a hit. Paired comparisons use the same tasks for both
configurations: mean per-task difference, percentile bootstrap 95% interval
(2000 resamples, seed 20261031), and wins/ties/losses.

## Configurations

| name | retrieval | selection |
|---|---|---|
| `truncation` | bm25 | render ranked fragments, cut the token sequence at the budget |
| `bm25_greedy` | bm25 | Phase 1 rank-order greedy (whole fragments only) |
| `graph_greedy` | bm25_graph | rank-order greedy |
| `hebra_optimized` | bm25_graph | optimized (`docs/optimizer.md`) |
| `ablation_no_graph` | bm25 | optimized |
| `ablation_no_coverage` | bm25_graph | optimized with `beta = gamma = 0` |

Budgets: 1000, 2000, 4000, 8000 tokens (o200k_base). Freshness filtering and
memory are not ablated here: every task is a clean checkout, so the freshness
filter never fires, and the dataset has no memory records. Their correctness is
measured separately ([Memory freshness](#memory-freshness)).

## Results, v1 (`benchmarks/results/v1-heldout`, Hebra `dedba7ca`)

Held-out, 90 tasks. Mean symbol recall:

| config | 1000 | 2000 | 4000 | 8000 |
|---|---|---|---|---|
| truncation | 0.283 | 0.433 | 0.539 | 0.739 |
| bm25_greedy | 0.235 | 0.411 | 0.507 | 0.728 |
| graph_greedy | 0.241 | 0.417 | 0.506 | 0.700 |
| hebra_optimized | 0.154 | 0.283 | 0.407 | 0.572 |
| ablation_no_graph | 0.169 | 0.300 | 0.406 | 0.622 |
| ablation_no_coverage | 0.126 | 0.283 | 0.396 | 0.580 |

Ranking: BM25 recall@10 0.504, recall@20 0.730, MRR 0.275; `bm25_graph`
recall@10 0.504, recall@20 0.669, MRR 0.274.

**Findings.** The v1 `optimized` strategy was significantly worse than
rank-order greedy at every budget (paired difference -0.08 to -0.16 symbol
recall, 95% intervals excluding zero). Simple truncation was the best
configuration. Graph expansion did not help: it changed little at small
budgets and lowered recall@20 by pushing BM25 hits below rank 20.

**Diagnosis (dev split only).** At 4000 tokens, `optimized` packed 19.6
fragments of 216 tokens on average at mean rank 16.9, against greedy's 11.7
fragments of 372 tokens at mean rank 6.9. Every label-bearing fragment that
greedy kept and `optimized` dropped was a large fragment at rank 1 to 3. The
v1 rank prior `10 / (10 + rank - 1)` decays so slowly that many small,
low-ranked fragments together outscore one large, top-ranked fragment, and the
cost-benefit ratio then prefers them. Truncation wins for a related reason:
it includes the beginning of large top-ranked functions that greedy skips
whole.

**Change.** The prior became `rank ** -k`, and the dev-only grid search was
extended to choose `k` (`benchmarks/results/v2-dev-tuning`). It chose `k = 2`
(the largest value in the grid), `beta = 0` (no query-term coverage), and
`gamma = 0.5`. Disclosure: this redesign was prompted by the v1 held-out
results, although the diagnosis and the tuning used dev tasks only. The v1
records are kept unchanged.

**Pre-registered decision (written before the v2 held-out run).** `optimized`
becomes the default only if, on held-out tasks, its paired symbol-recall
difference against `bm25_greedy` has a 95% interval entirely above zero at at
least three of the four budgets. Otherwise `greedy` stays the default.

## Results, v2 (`benchmarks/results/v2-heldout`, Hebra `98e9dc5a`)

Held-out, 90 tasks, same dataset and protocol. Mean symbol recall:

| config | 1000 | 2000 | 4000 | 8000 |
|---|---|---|---|---|
| truncation | 0.283 | 0.433 | 0.539 | 0.739 |
| bm25_greedy | 0.235 | 0.411 | 0.507 | 0.728 |
| graph_greedy | 0.241 | 0.417 | 0.506 | 0.700 |
| hebra_optimized | 0.213 | 0.365 | 0.498 | 0.620 |
| ablation_no_graph | 0.252 | 0.389 | 0.480 | 0.730 |
| ablation_no_coverage | 0.226 | 0.389 | 0.489 | 0.680 |

Paired difference, `hebra_optimized` minus `bm25_greedy` (95% interval,
wins/ties/losses):

| budget | v1 | v2 |
|---|---|---|
| 1000 | -0.082 [-0.165, -0.004] | -0.022 [-0.067, 0.011], 2/85/3 |
| 2000 | -0.128 [-0.219, -0.039] | -0.046 [-0.107, 0.009], 3/81/6 |
| 4000 | -0.100 [-0.185, -0.015] | -0.009 [-0.074, 0.059], 7/77/6 |
| 8000 | -0.156 [-0.248, -0.067] | -0.107 [-0.191, -0.030], 5/70/15 |

**Decision.** The pre-registered criterion was not met (no budget has an
interval above zero), so `greedy` remains the default and `optimized` is an
opt-in experimental strategy.

**Findings.**

- The steeper rank prior removed most of v1's deficit at 1000 to 4000 tokens,
  where `optimized` and `greedy` are now statistically indistinguishable. It
  is still worse at 8000 tokens.
- The cause at 8000 is graph-symbol coverage: removing the graph from the
  optimizer (`ablation_no_graph`) recovers +0.109 [0.030, 0.187]. On dev at
  8000 tokens, 9.1 of the 27.5 fragments `optimized` selects with graph
  retrieval came only from graph expansion, displacing BM25-ranked fragments.
- Graph expansion with greedy selection (`graph_greedy`) is indistinguishable
  from BM25 at every budget, and lowers ranking recall@20 from 0.730 to 0.669.
  On this task type (localizing the code a fix changed, from a one-line
  description), one-hop call and reference neighbors rarely contain the
  changed code.
- Truncation remains the strongest configuration (best mean at every budget,
  though not significantly better than greedy at most budgets). It includes
  the beginning of large top-ranked functions that whole-fragment strategies
  skip. Including a bounded prefix of a large fragment, with correct line
  numbers, is the most promising direction suggested by these data; it is
  not implemented.
- The 30-task dev split did not predict held-out behaviour: on dev, v2
  `optimized` was slightly ahead of greedy at 8000 tokens (+0.05; 2 wins,
  1 loss). Small tuning sets are a limitation of this study.
- On the 68 held-out tasks whose subject does not name a label, the pattern is
  the same (see `summary.md`).

Every packed context in every run stayed within its budget, and every
reference matched the file at its stated lines (`references correct` = 1.0).

Indexing (first full index of a checkout; later tasks re-index incrementally):
click 0.46 s, requests 0.27 s, attrs 0.40 s for 110 to 140 files on an Apple
Silicon laptop; median incremental re-index 0.12 to 0.16 s. Median
`hebra pack` latency at 4000 tokens: 17 ms (greedy), 23 ms (optimized),
10 ms (truncation). Timings are from single runs on one machine.

Memory freshness (`benchmarks/results/v2-memory-freshness`): 15 of 15
constructed scenarios classified as intended.

## Memory freshness

`benchmarks/memory_freshness.py` builds 15 scenarios (unchanged file, edits
inside and outside the referenced lines, moved lines, deletion, rename,
symlink replacement, branch switches and resets with and without content
changes, decisions, records without references, and a store copied into an
unrelated repository) and compares the computed status with the status each
scenario was constructed to produce. These labels are correct by
construction, so this checks that freshness detection implements its
documented semantics; it does not show that memory helps an agent.

## Agent benchmark

`benchmarks/agent_harness.py` prepares per-task prompts (task plus Hebra's
packed context) and, only with `--runner CMD --max-tasks N
--i-accept-the-cost`, runs an external agent command, checks whether its patch
applies, and optionally runs a test command. No runner was configured and no
agent results exist. Retrieval results above must not be read as evidence that
agents succeed more often.

## Reproducing

```bash
python benchmarks/mine_tasks.py benchmarks/configs/v1.json CACHE benchmarks/tasks/v1.jsonl
python benchmarks/tune.py benchmarks/configs/v1.json benchmarks/tasks/v1.jsonl CACHE OUT
python benchmarks/run.py benchmarks/configs/v1.json benchmarks/tasks/v1.jsonl CACHE OUT --split heldout
python benchmarks/summarize.py OUT benchmarks/tasks/v1.jsonl
python benchmarks/memory_freshness.py OUT
```

`CACHE` holds the cloned repositories (about 40 MB). Each results directory's
`manifest.json` records the Hebra commit, dataset and config hashes, platform,
tokenizer, and seed; `summarize.py` refuses to summarize records whose hashes
do not match.
